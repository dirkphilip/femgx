# Viewer conformance matrix

This matrix turns the minimum trustworthy CAD/FEM viewer contract into an
auditable test map. The authoritative capability scope remains
[[requirements/product-scope|Product scope]]; this note records how the current
implementation demonstrates that the in-scope basics work and where evidence
is still incomplete.

Tests provide repeatable evidence, not a mathematical guarantee against every
browser, driver, or model. The confidence floor is strongest when a requirement
is protected at three layers: validated construction or pure invariants,
CPU-to-GPU contract tests, and real hardware-WebGPU behavior.

## Evidence levels

- **Strong** — invalid state is rejected at its owner and deterministic tests
  protect the important boundary, inverse, round-trip, or identity relations.
- **Hardware-local** — real WebGPU pixels, depth, picking, or interaction are
  covered by the required local system-Chrome lane, but not by hosted merge CI.
- **Partial** — useful targeted evidence exists, but an important state sequence
  or end-to-end relation is not yet exercised systematically.

## Merge guarantee today

Every pull request must pass construction, invariant, CPU-to-GPU layout,
coverage, performance-budget, package, and unsupported-WebGPU tests in hosted
CI. Rendering, depth, picking, lighting, and responsive evidence additionally
requires `npm run test:e2e` on system Chrome with hardware WebGPU before a
rendering-related change is merged.

This is not yet one fully automated merge guarantee: hosted CI has no real-GPU
runner. A green hosted build proves the non-visual contract and the explicit
unsupported path; it does not prove that a real adapter presented correct
pixels.

## Highest-value gaps

1. **Hardware WebGPU in CI.** Run the existing `chrome` project on a real-GPU
   runner. Do not substitute SwiftShader or weaken capability assertions.
2. **Focused state-handoff regressions.** When a camera, runtime, visibility,
   deformation, recovery, or pick snapshot bug is found, protect the shortest
   operation sequence that reproduces the stale state at its owning boundary.
   Do not add broad randomized sequences or duplicate subsystem assertions.
3. **Explicit audit maintenance.** When a core requirement changes, update its
   matrix row in the same change. A row may become stronger only when its cited
   evidence protects the stated invariant.
